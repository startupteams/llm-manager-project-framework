# Developer, Build, and Setup Commands

This repo captures the **deployed** LLM Manager service on VM114 (MARION-IA-USA) as of 2026-09-25. There is no separate build system: the deployed layout *is* the source layout. This doc describes how to reproduce, run, and modify it.

## Repo-to-deployment map

| Repo path | Deployment path (VM114) | Notes |
| --- | --- | --- |
| `service/app/` | `/opt/llm-manager/app/` | FastAPI web shell (`main.py`), API core (`v011_core.py`), recovery engine (`v011_recovery.py`), spend guard, LiteLLM sync, cost gate tests |
| `service/collectors/` | `/opt/llm-manager/collectors/` | GPU power sampler (20 s) + Emporia facility adapter |
| `service/control/` | `/opt/llm-manager/control/` | Allowlisted Proxmox ops shim (`pve_ops.py`) |
| `ops/systemd/` | `/etc/systemd/system/` | Six units + `litellm.service.d/env.conf` drop-in |
| `ops/nginx/llm-manager` | `/etc/nginx/sites-enabled/llm-manager` | Public front door (:80 → :443, routes to 8001/4000/8200) |
| `ops/litellm/` | `/etc/llm-manager/` | `litellm_config.yaml` (generated by `litellm_sync.py`), env var *names* only, `routing_logger.py` |
| `config/examples/` | — | `requirements-v011-venv-freeze.txt` (118 pins, venv on deployment) |
| `db/schema/schema.sql` | PostgreSQL on CT115 | Schema-only dump (`pg_dump --schema-only`), no row data |

Secrets are **not** in this repo. The deployment reads them from root-owned files under `/etc/llm-manager/secrets/` (Postgres app creds, PVE token, LiteLLM salt, Emporia creds) and `EnvironmentFile=/etc/llm-manager/litellm.env`.

## Runtime baseline (deployed)

- Ubuntu 24.04 (VM114), system Python **3.12.3** (see `config/examples/runtime-python-version.txt`)
- App venv: `/opt/llm-manager/venv` (uvicorn, FastAPI, psycopg2-binary, ldap3, apscheduler, litellm, … — see the freeze file)
- Web shell: `uvicorn main:app --host 127.0.0.1 --port 8001 --workers 2`
- LiteLLM proxy: `litellm --config /etc/llm-manager/litellm_config.yaml --host 127.0.0.1 --port 4000`
- Database: PostgreSQL (CT115 @ 10.0.20.116), app connects with a scoped role via DSN in `/etc/llm-manager/secrets/pg_app_creds`

## Local development setup

```bash
# 1. Python + venv (3.10+; deployment runs 3.10.12)
python3 -m venv .venv && source .venv/bin/activate
pip install -r config/examples/requirements-v011-venv-freeze.txt

# 2. Provide secrets locally (NEVER commit these):
#    export PG_HOST/PG_PORT/PG_DB/PG_USER/PG_PW  (or replicate the creds-file layout)
#    export PVE_TOKEN=...                         (only for control-shim work)

# 3. Run the cost integrator gate (no DB/network needed):
python3 service/app/v011_cost_tests.py   # exit 0 = pass

# 4. Byte-compile everything as a smoke check:
python3 -m py_compile service/app/*.py service/collectors/*.py service/control/*.py

# 5. Run the web shell against a dev database:
cd service/app && uvicorn main:app --host 127.0.0.1 --port 8001 --reload
```

The web shell expects LLDAP (LDAP on port 3890) for `/login`; for local dev, front it without nginx or stub the LDAP host as needed.

## Deployment operations (VM114)

```bash
# Status / logs
systemctl status llm-manager-web llm-manager-recovery llm-manager-collector \
                 llm-manager-emporia litellm
journalctl -u llm-manager-web -u llm-manager-recovery --since "10 min ago"

# Apply a code change (edit /opt/llm-manager/app/*.py as root, then):
python3 -m py_compile /opt/llm-manager/app/v011_core.py   # syntax gate
systemctl restart llm-manager-web llm-manager-recovery

# Regenerate LiteLLM routing after registry/model changes:
/opt/llm-manager/venv/bin/python3 /opt/llm-manager/app/litellm_sync.py
systemctl restart litellm

# nginx changes
nginx -t && systemctl reload nginx
```

**Registry/alias caution (from live operations):** the `fast`/`code`/`frontier` alias targets are hardcoded in `v011_core.py` `sync_registry()`. Editing the `model_registry` table alone does **not** survive the next recovery-engine tick — change the alias tuple in source, then restart `llm-manager-web` + `llm-manager-recovery` and regenerate LiteLLM config.

## Database

- Schema-only reference: `db/schema/schema.sql` (generated with `pg_dump --schema-only`; safe to read/commit).
- Migrations today are **additive SQL applied by hand** (e.g. `deployment_revisions`, extended `benchmark_runs`). There is no migration runner yet — see `docs/tdr/` for the formalization TDR. Until one exists, record every schema change as a numbered SQL file here and in the deployment journal.
- Never commit row dumps, `pg_dump` without `--schema-only`, or connection strings with credentials.

## Adding/changing an endpoint (typical loop)

1. Edit `service/app/main.py` (route) and/or `v011_core.py` (logic).
2. `py_compile` gate → restart web unit → verify against `/api/status` or the specific route.
3. Update `docs/OPERATIONS_AND_USAGE.md` endpoint table in the same PR.
4. Keep changes small and reversible; the deployment has no separate staging environment.
